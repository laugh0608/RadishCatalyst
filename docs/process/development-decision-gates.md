# Development Decision Gates

更新时间：2026-07-04

## 用途

本文定义玩家可见开发包的决策闸门，防止项目在截图调参、文档口径修正、检查接线或同类实现补丁中反复打转。

本流程不替代 `docs/planning/current.md` 的阶段边界，也不替代 `docs/features/` 的具体功能范围；它只约束每次开发前后如何判断“继续、停手、换路线或拆专题”。

## 适用范围

必须使用本闸门的情况：

- 玩家可见画面、玩法、HUD、场景、叙事节拍或交互反馈开发包。
- 同一问题已经经过一次实机截图 / 录像复核但仍未达标。
- 需要修改 `docs/planning/current.md`、`docs/planning/daily-start.md`、`AGENTS.md`、`CLAUDE.md` 或验证基线。
- 自动检查通过但玩家观感、玩法理解或体验目标仍明显失败。

可跳过的情况：

- 单点 typo、链接、格式、脚本路径或文案修正。
- 不影响玩家体验、阶段边界和验证基线的小范围代码修复。

## 开工前五问

每个玩家可见开发包开工前，先在专题或工作说明中回答：

1. 玩家结果：完成后玩家会看到什么、做什么、理解什么？
2. 实现介质：目标需要程序绘制、sprite、tile、atlas、场景节点、HUD 组件、数据规则，还是组合方案？
3. 成功证据：什么截图、录像、人工复测或自动检查能证明它成立？
4. 失败判据：什么结果说明当前路线不成立，而不是只差一次调参？
5. 文档落点：这次信息应进入入口、专题、周志、参考资料，还是无需改文档？

没有明确玩家结果和实现介质时，不应直接进入代码实现。

## 证据分层

- 自动检查：证明数据、接线、场景引用、运行时脚本和回归没有明显断裂。
- 实机截图 / 录像：证明玩家可见画面、层级、主体读法、HUD 遮挡和空间关系成立。
- 人工路径复测：证明玩家能完成目标、理解下一步并感到循环成立。

玩家可见目标不能只用自动检查判定通过。自动检查全绿但实机观感失败时，应按失败处理。

## 两次失败停手规则

同一个玩家可见问题若连续两次采用同类方案仍未通过实机复核，必须停止继续追加同类开发包，并做路线复盘。

同类方案包括：

- 继续加透明层、线框、箭头、焦点框、标签或 debug cue。
- 继续堆提示文案、状态字段、设备面板字段或检查断言。
- 继续在同一程序绘制层上加局部形状，却没有改变实现介质。
- 继续围绕同一截图点做同层级调参。

路线复盘必须给出结论：

- 继续：当前路线仍成立，只需一个明确收尾包。
- 换介质：改用资产、tile、sprite、场景节点、组件或数据结构。
- 拆专题：问题已超出现有专题职责，需要新细专题承载。
- 降范围：目标过大，先做更窄的玩家可见成果。
- 暂缓：当前不是阶段阻塞，进入 backlog 或后续 polish。

## 架构级升级点

日常开发由执行会话（任意模型）直接推进；遇到以下决策时执行会话应停手，把问题连同证据升级给萝卜SAMA，由架构复核会话处理：

- 画面介质或风格锚点变更：更换 / 重生成 `assets/reference/style-anchor.png`，或修改提示词库的调色板、视角、尺寸口径。
- 阶段与专题变更：切换 `docs/planning/current.md` 阶段、建立 / 取代 feature 专题、判定阶段退出条件达成。
- 两次失败停手规则触发后的路线复盘决策。
- 存档结构、联机边界或跨系统架构调整。
- `P3` 旧视觉层大规模删除收口的最终复核。
- `AGENTS.md`、`CLAUDE.md`、规划入口口径或验证基线本身的修改。

无需升级的日常执行：按提示词库生成与审阅素材、裁切缩放接入、`TileMapLayer` / 设备场景实施、按专题清单删除旧视觉层、修剪失效检查、常规提交与周志记录。

## 文档落点规则

- `docs/planning/current.md`：只记录阶段、活跃专题、冻结项、退出条件和当前边界。
- `docs/planning/daily-start.md`：只记录日常入口、读取顺序、当前重点和下一步，不记录包流水。
- `docs/features/`：记录玩家目标、实现范围、边界、验收和当前细专题。
- `docs/devlogs/`：记录过程、提交回顾、失败复盘、关键决策和验证结果。
- `docs/reference/`：记录长期可参考材料、分析和外部建议。
- `docs/archive/`：记录历史原貌，不作为当前规范。

如果一次改动只是“这包做了什么”，优先写周志；如果一次改动改变“接下来怎么做”，才更新规划入口或专题边界。

## 路线复盘模板

当触发两次失败停手规则时，按下面结构记录在专题或周志中：

```text
问题：
目标：
已尝试方案：
实机失败证据：
根因判断：
决策：继续 / 换介质 / 拆专题 / 降范围 / 暂缓
下一步玩家可见结果：
不再继续的做法：
验证方式：
```

## 当前案例

2026-06-25 的基地首屏 UI / Art 第十四到十七包连续证明：继续在程序几何图层上叠加 `draw_line`、`draw_rect`、圆环和半透明多边形，只能把画面推到低保真示意图，不能接近参考图的资产化游戏场景。

因此首屏后续决策为“换介质 + 拆专题”：转入 [Demo First Screen Assetized Scene V1](../features/demo-first-screen-assetized-scene-v1.md)，以低保真地貌、晶体、污染、设备、管线和角色资产作为主读法。

2026-07-12 的 `R2-A` 又证明：单张生成式宽幅场景板能改善统一透视和整景气质，但不能稳定同时控制玩法路径、交互插槽、静态 / 交互语义与 HUD 安全区。两轮各 3 张候选均未达到接入条件，因此停止同类生成，并把决策从“再换一种画面介质”升级为 [项目目的与个人 + AI 开发方式复盘](../planning/project-purpose-and-solo-ai-development-review.md)。复盘完成前暂停所有实现线。
