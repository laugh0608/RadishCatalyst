# Development Retest Baselines

更新时间：2026-06-08

## 文档目的

这份文档定义首小时原型当前使用的“开发复测基线”。

它回答三件事：

- 为什么不应再把“每次人工复测都从空档重打”当默认。
- 当前有哪些标准阶段基线，分别适合复测哪一段。
- 开发时应该怎样在“局部基线复测”和“全链路空档复测”之间做取舍。

## 设计目标

开发复测基线的目标不是替代空档复测，而是把空档复测从“每次都做”降级为“在真正需要时做”。

当前设计遵守以下原则：

- 基线由代码生成，不手工维护长期 JSON 快照。
- 基线必须同时覆盖任务状态、区域解锁、场景完成态、敌人状态、已建结构和关键库存。
- 基线必须能直接载入当前运行时，不要求先跑外部脚本。
- 载入基线后，若需要长期保留，仍可保存到普通槽位。
- 新内容扩展时，优先补对应基线，而不是让人工复测链无限变长。

当前运行时实现位于：

- `client/scripts/save/development_baseline_catalog.gd`
- `client/scripts/save/development_baseline_builder.gd`
- `client/scripts/ui/hud_development_baseline_presenter.gd`

## 核心稳定站人工短跑基线

核心稳定站终点链已登记为代码生成 `S21` 基线。人工短跑优先从 `S21` 切入：确认地图 / HUD 指向 `region.demo_stabilization_core`，再跑核心稳定站终点链。若本地已有高压窗口归档后的普通槽位，也可直接载入该槽位。

短跑步骤：

1. 从高压窗口反馈归档后出发，确认当前目标指向核心稳定站，且未要求再新增行动台方案或高压窗口分支。
2. 进入 `region.demo_stabilization_core`，确认 `quest.enter_demo_stabilization_core` 完成，并激活 `quest.prepare_demo_stabilization_buffer`。
3. 返回污染边界末端回收补料沉积物并清理补料守卫，回处理点过滤出抗污染药剂和污染浆液，再回基地用基础反应器整备 `item.core_stabilization_buffer`。
4. 确认核心稳压缓冲包目标完成并激活阶段守卫目标；带核心稳压缓冲包回核心稳定站后，可先回收侧边补给缓存取得修复凝胶和抗污染药剂，再击败 `enemy.demo_stabilization_guard`，守卫第一次回写压力应消耗缓冲包并降低生命 / 防护承压。
5. 击败守卫后回收 `map_object.demo_stabilization_guard_cache`，确认拿到 `item.core_write_charge`、基础零件和终点前补给；若未回收校验片，核心设备应拒绝写入。
6. 在 `map_object.demo_stabilization_core` 写入稳定数据；若已回收核心站侧边补给、阶段守卫反击消耗过核心稳压缓冲包或带有抗污染药剂，设备写入应读取这些终点前整备并降低反冲；没有药剂时仍可完成但承压更高。
7. 完成后检查 HUD / 地图 / 任务追踪不再把玩家引回行动台、高压窗口或新的区域入口。

污染边界门前短跑补充：从 `S1` 后半段或普通进度进入污染边界深处时，带有抗污染药剂攻击门前受扰敌人，应自动消耗 1 个药剂并降低首次反击承压；没有药剂时仍可清理敌人，但门前压力完整命中。

遗迹外圈短跑补充：从 `S2` 进入 `quest.salvage_signal_echo` 时，带基础过滤模块清理 `enemy.ruin_phase_guard` 应明显降低外圈回波反击造成的生命 / 防护承压；无模块仍可清理守卫，但战后更依赖修复凝胶和过滤器处理回波沉积。

`S2` 回基地解析深段回波时，`recipe.deep_signal_analysis` 应消耗 `item.signal_echo_trace` 和 `fluid.polluted_slurry`；若缺污染浆液，设备缺料提示应指回相位守卫后暴露的污染回波沉积过滤线。

污染过滤器补充：`recipe.cleanse_residue` 完成后的下一步应按当前任务分流；组装稳相信标时指向 `recipe.phase_anchor`，回收深段回波时指向回波匣和裂相坐标解析，核心缓冲包整备时指向 `recipe.core_stabilization_buffer`，门前压力尚未处理时指向带药剂回污染边界排压。

检查口径：

- 自动检查已覆盖区域边界、地图标记、任务规则、守卫门控和核心设备写入事件；若 `pwsh ./scripts/check-client.ps1` 因 Godot 4.6.2 原生崩溃中断，应记录崩溃发生的子检查，不把未完成聚合检查写成通过。
- 人工短跑只阻塞 `P0` / `P1`：崩溃、主线卡死、坏档、任务无法完成、核心资源断档，或 UI 完全无法判断下一步。
- 文案密度、局部路径拥挤、战斗数值偏软 / 偏硬、资源点数量不足先记入后续核心区域尺度规划，不阻塞 demo 收束阶段。
- 若后续调整该切点，应同步更新 `DevelopmentBaselineCatalog`、`DevelopmentBaselineBuilder`、`development_baseline_save_check.gd` 和相关 HUD 基线展示检查。

## 运行时使用方式

当前原型里，按 `Tab` 打开左侧调试面板后，会看到“开发基线”区。

使用步骤：

1. 点击“上一个 / 下一个”切换基线。
2. 点击“载入”把当前运行时重置到该阶段。
3. 如需长期保留，再用现有普通槽位按钮保存到 `slot_01`、`slot_02` 或 `slot_03`。

同一调试侧栏里现在还附带一组开发期 GM 控件：

- 可轮换关键资源并做 `+1 / -1` 数量调整。
- 可一键回满生命和防护。

它只服务本地开发复测，不面向正式玩家。

这套机制默认用于本地开发和人工复测，不面向正式玩家。

## 什么时候用基线

默认规则：

- 当前阶段若只改开局场景、首小时交互提示、设备面板、HUD 信息层级或核心区对象表现，优先执行 `check-client` 和对应局部 UI / 场景断言；人工复测优先从 `S0`、`S1` 或 `S21` 取样，不再沿 `S16` 到 `S20` 中段链路逐段重跑。
- 只改风蚀张力核解析、张力绕轮、纬束残团、风蚀梭栓或风蚀管廊，优先从 `S10` 开始。
- 只改锁相织构核解析、边缕残条、锁相键栓或锁相框架，优先从 `S11` 开始。

## 什么时候仍然必须跑空档

以下情况不应只依赖局部基线：

- 当前「首版 Demo 冷启动试玩审计」必须从 `S0` 新档开始，局部基线只用于定位已发现的问题段。
- 改了早期主线顺序或新档初始状态。
- 改了共享任务推进、区域解析、地图目标来源、HUD 全局提示口径。
- 改了存档迁移、存档校验或旧进度补激活逻辑。
- 改动跨越多个阶段，且你怀疑基线之间的衔接本身可能出错。
- 一个较大功能包准备收口，想确认从头到尾仍然通顺。

这类情况仍应补一轮 `S0` 全链路复测，必要时再配合中后段基线做局部追踪。

## 维护规则

新增或调整首小时内容时，如果影响了标准阶段切点，需要同步更新三处：

1. `DevelopmentBaselineCatalog` 的阶段定义和用途描述。
2. `DevelopmentBaselineBuilder` 的任务推进、场景完成态和库存口径。
3. 相关检查与文档，确保基线、任务链和人工复测规则一致。

如果某个阶段已经不再适合作为稳定复测起点，应替换它，而不是继续堆更多一次性临时快照。

## 当前结论

首小时原型后续继续扩展时，人工复测的默认姿势应改为：

**先从最接近问题的开发基线开始，再决定是否需要回到 `S0` 全链路重跑。**
