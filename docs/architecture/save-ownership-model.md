## 7. 存档归属模型

建议明确区分三类存档或档案：

### 7.1 世界存档

用于保存：

- 地图进度
- 建筑布局
- 设备状态
- 管网状态
- 储罐内容
- 电网状态
- 区域解锁
- 主线推进
- 世界任务状态
- 基地库存

它代表的是“这个世界本身”。

### 7.2 玩家档案

用于保存：

- 账号显示名或头像设置
- 输入设置
- 辅助功能设置
- 已知服务器、好友和账号信息
- 成就或全局解锁

它代表的是“这个玩家自己”。

玩家档案不应直接等同于某一个角色。一个玩家可以拥有多个角色。

### 7.3 角色档案

用于保存：

- 角色 ID
- 角色名和外观
- 初始背景或角色原型
- 初始能力
- 初始天赋
- 等级
- 技能
- 装备
- 快捷栏
- 个人背包
- 个人任务进度
- 与某个世界的绑定关系

它代表的是“这个玩家当前使用的具体角色”。

### 7.4 单机模式下的关系

单机时，世界存档和玩家档案可以一起保存在本地。

同一个玩家可以在不同本地世界中选择不同角色。不同角色可以拥有不同初始能力和天赋，用于支持不同 Build、不同开局体验和不同协作分工。

### 7.5 开房模式下的关系

开房时：

- 世界存档归房主
- 其他玩家带入自己的角色档案，选择一个角色加入，或使用房间规则指定的临时角色

建议优先考虑三种模式：

1. 角色绑定世界  
进入某个世界时，角色成长跟随该世界推进

2. 角色弱绑定世界
角色可以由玩家选择进入多个世界，但等级、装备、背包或关键进度根据世界规则限制

3. 临时房间角色
加入某个世界时按房间规则生成临时角色，离开后只保存有限个人进度或不保存

从开发复杂度和平衡看，首版建议优先：

**角色与世界弱绑定，但跨世界资源、装备、配方和任务推进携带要严格限制。**

推荐规则：

- 同一个玩家可以创建多个角色。
- 不同存档可以选择不同角色。
- 同一角色进入不同世界时，可以保留外观、基础天赋和部分个人成长。
- 资源、装备、基地解锁、区域进度和主线推进默认跟随世界存档。
- 房主或服务器应能决定是否允许外部角色加入。
- 如果允许外部角色加入，应有等级、装备、背包或材料携带限制，避免破坏世界进度。

### 7.6 初始能力与天赋

不同角色可以有不同初始能力和天赋，但它们应服务协作和 Build 倾向，而不是变成不可逆职业锁死。

推荐初始倾向：

- 工程倾向：建造、修复、部署装置或设备排障更强。
- 外勤倾向：移动、采集、扫描或背包效率更强。
- 战斗倾向：武器操控、输出、控场或弱点打击更强。
- 生存倾向：环境抗性、治疗、撤离或补给效率更强。

设计边界：

- 初始天赋不能替代基地生产和装备成长。
- 不同角色应能通过装备、模块和技能形成混合 Build。
- 首版不做复杂职业树，优先做少量清晰初始差异。
- 联机协作可以鼓励分工，但单机角色必须也能完整通关首版闭环。

### 7.7 本地存档阶段策略

#### 当前切片执行口径（2026-07-26）

当前切片已按 [Slice Multi-World Save List V1](../features/slice-multi-world-save-list-v1.md) 完成最多 30 个本地世界的目录、列表与游戏内返回：

- 最多 30 个本地世界；上限只计算世界，不计算备份。
- 一个稳定世界 ID 对应一个目录、`metadata.json`、一个权威 `autosave.json` 和三份备份；显示名变化不改变 ID。
- `SliceSaveCatalog` 负责枚举、创建、重命名、可恢复回收、损坏项隔离和目录安全；单世界 `SliceSaveService` 继续独占 schema 6 玩法状态。
- `Boot` 只在创建或选择后注入该世界服务；`Esc` 暂停的保存返回成功后释放世界、清空服务并重建列表。
- 旧切片单档先校验、复制、读回后导入第一个命名世界，旧文件保留；迁移失败不创建半成品世界。
- 自动测试使用可注入的独立世界根，最终通过态和主档 / 备份保留供人工复核，不污染正式存档。
- 玩家 / 角色档案拆分、云存档、手动快照和跨世界携带仍未实现。

当前目录：

```text
user://saves/slice/
  worlds/
    world_<stable_id>/
      metadata.json
      autosave.json
      backups/
        autosave.bak.1.json
        autosave.bak.2.json
        autosave.bak.3.json
  trash/
    <recoverable_entry>/
```

规则：

- `metadata.json` 保存世界 ID、显示名、创建 / 更新时间、版本与轻量摘要，不承载玩法权威状态。
- `autosave.json` 是默认进入世界时读取的主文件。
- `backups/` 中保留最近 3 份可读取备份。
- 备份轮转顺序为：写入新主存档前，将 `bak.2` 移为 `bak.3`，`bak.1` 移为 `bak.2`，当前 `autosave.json` 复制为 `bak.1`。
- 如果备份轮转失败，不允许覆盖当前主存档。
- 回收只移动完整世界目录；恢复不覆盖同 ID 在用世界，回收项不计入 30 世界上限。

#### 后续角色档案与手动快照

当前先把背包、玩家位置和后续角色强化随世界保存；等角色所有权稳定后，才考虑增加：

```text
user://saves/
  profile/
    local_profile.json
  characters/
    character_<stable_id>.json
  worlds/
    world_<stable_id>/
      metadata.json
      autosave.json
      manual_001.json
      backups/
```

规则：

- 世界进度、基地、区域、任务、建筑、设备和世界库存归属 `worlds/world_<stable_id>/`。
- 角色外观、装备、快捷栏和个人背包目前随世界存档保存；迁出前必须先定义跨世界携带限制。
- `local_profile.json` 只保存本地设置、最近进入世界、显示偏好和非关键个人配置。
- 手动存档可以作为同一世界下的额外快照，但不能变成跨世界资源转移入口。

#### 迁移与恢复

当前只自动迁移上一版切片单档 `user://saves/slice/slice_world.json` 及其单份 `.bak`：

1. 没有现有世界时才尝试迁移，避免重复导入。
2. 先按 schema 2–6 读取并校验，再生成新的 `world_<stable_id>/metadata.json` 和 `autosave.json`。
3. 复制后必须用新世界服务读回，成功才发布目录；原旧档保留为只读迁移源。
4. 迁移失败时保留旧档、报告原因并清理半成品，不覆盖任何已存在世界。

坏档恢复优先级：

1. 尝试读取主存档。
2. 主存档缺失或校验失败时，尝试读取 `backups/autosave.bak.1.json`。
3. 继续失败则尝试 `bak.2`、`bak.3`。
4. 所有备份失败时，保留坏档文件并在列表把该世界标为不可载入；其他世界仍可正常使用。

恢复成功后，不应立刻覆盖原坏档；应等玩家再次主动保存或自动保存触发时再写入新的主存档。

### 7.8 联机与云存档边界

首版本地存档不依赖账号、网络或官方服务。

未来接入联机和云存档时，边界应保持：

- 房主开房时，世界存档仍归房主本地或专服。
- 专用服务器使用同一套世界状态结构，但保存位置从 `user://saves/` 迁到服务器数据目录。
- 官方云存档优先同步玩家档案、角色档案和世界备份元数据，不优先实时同步完整世界。
- 云同步必须以本地可读存档为基础，不能让离线单机变成在线依赖。
- 多人世界的冲突合并不在首版处理；Host / 专服是唯一权威写入者。
