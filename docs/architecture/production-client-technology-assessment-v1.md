## 结论与依据

建议正式游戏采用 **Godot 4.x 3D 桌面客户端**，以已获认可的 Web 三维画面、50° 视角、单枚接口箭头、拖动铺带与真实弯道为迁移验收标准。Web `/play/` 保留为可运行的体验参照，同规则 Godot Demo 对照已完成，后续按新首包专题收敛正式接入方案。

这是基于当前仓库与桌面游戏目标的工程判断，不是两套引擎的大规模性能实测结论。选择 Godot 的主要收益是继续利用已有的存档设施、库存与生产规则基础，以及游戏场景、资源导入和运行时工具；主要成本是拆开二维节点与权威状态的耦合，重做三维显示和输入映射，并证明新画面达到 Web 参照。不能把“仍用 Godot”解释成低成本一键转 3D。

Three.js + Electron 是可行的第二选择：画面与浏览器交互的直接复用更多，但桌面生命周期、持久化、进程通信、资源工作流与回归入口都需要建设。现有 Web 内容不足以抵消这些正式化工作。若首发改为浏览器免安装，或跨引擎画面迁移成为首要不可接受成本，应重新比较这条路线。

## 评估前提

- 产品以 [Production-Centered Direction](../product/production-centered-direction.md) 为准：化工生产经营为核心，探索提供资源、空间与目的；战斗、液气、多星球和随机投入的具体实现仍未解冻。
- 沿用 [Platform Targets](platform-targets.md) 的 Windows 桌面、离线单机作为比较前提；这不把较早的平台规划变成本次已批准决定。当前开发机上的结果不能代替 Windows 目标机证据。
- 长期世界保存是正式化要求；离线单机不等于关闭游戏仍累计生产。本次不引入离线收益。
- 既有 [Multiplayer Model](multiplayer-model.md) 的后续 Host 协作、权威状态同步作为扩展约束，不作为首包功能，也不等于目前已有多人实现。
- 最低硬件、正式工厂容量和帧率承诺尚未冻结。下文规模和预算是建议验证目标，不是产品承诺或已测上限。

| Godot 正式入口 | [Slice Runtime Systems](slice-runtime-systems.md) 记录 Boot、多世界、schema 10、三份备份、候选校验后发布、独立设置 | 存档设施已有实现与历史检查，迁移应保留其失败处理合同 |

| Godot 可复用边界 | `SliceSaveCatalog`、`SliceBuildingSaveCodec` 为 `RefCounted`，但后者仍引用旧目录、足印和建筑类型 | 可复用文件管理与校验思想，具体 schema / 类型约束须逐项复核，不能宣称零改动复用 |

评估形成时只核对源码、既有证据和官方能力文档；后续 Demo 与清晰度实测由其独立专题记录，不把它们或此前 Node 23 项检查混算为正式客户端回归。

## 路线比较

| 维度 | Godot 3D 桌面 | Three.js + Electron 桌面 |
| --- | --- | --- |
| 保持当前观感 | 需迁移几何、材质、灯光、相机与 HUD 并重新验收 | 可较多保留现有渲染与 DOM，但桌面窗口仍需复验 |
| 正式存档 | 有文件管理、备份与校验基础；三维状态和旧内容兼容仍需设计 | 有本地文件能力；须新建保存服务并重写或转译已有合同与检查 |
| 大工厂 | MultiMesh / 分区可减少绘制开销；模拟仍需数据化和增量拓扑 | InstancedMesh / 分区同样可优化；现有查找和渲染驱动需重整 |
| 游戏资源生产 | 有场景、动画与 3D 导入工作流；本仓库量产模型规范仍缺失 | 可以使用模型资产，但编辑、检查与运行时资源组织需组合工具 |
| 桌面与后台 | 沿既有项目管理窗口、输入、音频、生命周期；平台适配仍需测 | 增加 Electron 主进程、渲染进程和受限本地接口；重负载不能堵住窗口管理 |
| 后续联机 / 专服 | 有网络与 headless 基础；权威命令、同步和恢复仍须实现 | 独立 JS 模拟有复用潜力；网络协议、进程边界及服务端运行需要工程化 |
| 本项目主要风险 | 画面与手感回退，以及二维耦合拆分被低估 | 将当前小型页面当成完整游戏框架，长期同时维护多套基础设施 |

能力依据：Three.js 的 [InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html) 为共享几何与材质的实例减少 draw calls；Godot 的 [MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html) 同样面向大量实例，但单批不能逐实例裁剪，需要按区域组织。这些能力都不能替代生产模拟优化。

Electron 的 [Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model) 提供窗口、主进程、渲染进程和本地能力桥接，因此 Web 技术并不强制浏览器交付。若选它，本地文件接口应经隔离的有限 IPC 暴露，并持续维护运行时依赖，见 [Security](https://www.electronjs.org/docs/latest/tutorial/security)。这里的维护成本是桌面工程成本，不是判定 Web 做不了游戏。

Godot 支持 [glTF / GLB 场景导入](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)、[高层联机 API](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html) 和 [headless 专服运行](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html)。这些是引擎能力；本项目尚未实现联机，也未建立量产 3D 美术管线。

## 迁移工作与代价

以下高 / 中 / 低是相对工程量及回归面，不是工期估算。未给出天数，因为目标机、资源规格与存档兼容方案尚未冻结。

| 工作项 | Godot 3D | Three.js + Electron | 必须交付的结果 |
| --- | --- | --- | --- |
| 视觉与建造输入 | 高 | 低—中 | 50° 视角、端口、弯道、遮挡、拖铺及取消达到参照；三维射线落到逻辑格 |
| 生产权威状态 | 中—高 | 中 | 库存、在途货物、缓冲和加工进度不依赖可见节点；命令先校验再提交 |
| 长期存档 | 中—高 | 高 | 稳定 ID、版本校验、临时文件、备份、失败不覆盖、恢复后继续生产 |
| 桌面运行与入口 | 中 | 高 | 正式启动、世界选择、暂停、退出、设置与恢复路径 |
| 大工厂性能 | 高 | 高 | 模拟与渲染分别计量、占用索引增量维护、同类实例分区合批 |
| 量产资产规范 | 中—高 | 中—高 | 尺度、原点、足印、接口、材质和批次预算；当前程序几何不直接算量产管线 |
| 验证迁移 | 中—高 | 高 | 保留旧证据；新入口的规则、存读、窗口截图和目标机检查独立成立 |

Godot 路线按三类处理资产：稳定 ID、守恒规则和测试用例作为合同复用；文件管理与通用库存实现按依赖复核后复用；二维视图、像素坐标、碰撞、建造预览和 Web 输入代码重新适配。不要把旧 ARPG 任务与战斗整包带入当前生产包。

正式状态建议保留二维逻辑格坐标，三维高度与 X/Z 世界坐标由显示层映射。旧 schema 10 包含二维角色位置、固定地图与外勤状态，因此“改为 Vector3”不是兼容迁移方案。首包应明确新旧世界类型和隔离路径，复用已验证的文件设施，旧档保持可读；导入或 schema 升级必须有逐字段合同后才能实施。本次不决定新版本号、不删除旧档、不承诺自动导入。

## 建议的规模验证合同

正式容量未知，建议先设两个工程负载档位，避免以三机流畅代替扩展性判断：

| 档位 | 建议数据量 | 用途 |
| --- | --- | --- |
| 首阶段验收 | 100 台加工 / 采集 / 仓储设备、1,000 段带、最多 1,000 个在途物品 | 证明一个可扩建区域的生产、建造和存读可持续运行 |
| 扩展压力 | 1,000 台设备、10,000 段带、最多 10,000 个在途物品 | 寻找模拟、绘制、内存和保存的瓶颈；暂不作为首包硬承诺 |

负载需包含运行、缺料、满仓回压、汇流和连续拆改；分别测局部可见与拉远大面积可见。应由正式模拟创建合法状态，不能复制静态 Mesh 后声称工厂压力通过。

建议以 Windows 目标机、1920×1080、固定画质为验收环境，记录 CPU / GPU / 内存 / 驱动 / 构建版本；目标机尚未指定。首档候选预算为 60 FPS、帧时间 p95 ≤16.7ms、20Hz 模拟步耗时 p95 ≤10ms、连续运行 30 分钟无持续积压；预算需在开发包确认时冻结。压力档报告实际数值和退化原因，不降低实例数冒称通过。

计量应区分完整帧间隔、模拟步、CPU 渲染提交、可用时的 GPU 时间、draw calls、内存和存读停顿。验证同一命令序列在不同渲染帧率下不丢模拟时间，暂停 / 后台 / 恢复语义一致，保存前后物品守恒、加工进度和物流恢复正确。此处固定步进用于稳定模拟，不承诺跨平台锁步确定性。

本次没有这些负载的实测值，也未验证 Windows GPU、Electron 打包体积、长期内存或正式 3D 存读。若首档经具体瓶颈治理仍不达标，应以剖析结果调整数据结构、实例批次或热点实现，再决定是否重开路线；不能从“换引擎”直接推导性能提升。

## 确认后的首个正式开发包

建议首包为“正式三维工厂基础与持久化”，在正式 `client/` 体系中接入受控入口，成果持续保留，验收包含：

1. 先冻结功能专题：新旧世界边界、逻辑格与显示坐标、Web 操作参照、首档负载和目标硬件；明确供电、构件来源与仓储规则，不能默认混合两套样件规则。
2. 在正式入口实现三维场地、角色、三机与固体带网；采用稳定实例 ID 和独立生产状态，支持放置、拖铺、拆回、缺料、回压与恢复。
3. 接入版本化存档与退出恢复：关闭游戏再进入，设备、库存、在途货物与加工进度一致，继续产出；坏主档可恢复备份，全部损坏时明确失败且不覆盖现有状态。
4. 完成同视角画面对照、真实操作路径和首档性能证据。新画面获认可前不删除 Web 参照或替换旧正式默认入口；这属于正式迁移验收，不再新建一次性视觉项目。

首包之后才讨论“产物换取构件并扩建”的玩家循环，液气、多人和更大地图另行设计。首包不批量重做全部美术，不一次搬完旧内容，也不打包发布。

当前已按用户认可与下一步授权进入 Godot 3D 首包设计；需审阅的是新专题里具体的 **正式入口、新旧世界隔离、工厂存档与扩建 / 负载合同**。合同通过后按 P1–P3 实施，不重复要求同范围画面认可。依赖安装、外部资产、打包发布仍按各自实际范围授权。
