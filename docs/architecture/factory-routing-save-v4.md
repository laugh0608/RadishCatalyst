# Factory Routing Save V4

更新时间：2026-10-12

## 范围与身份

对应已确认的[分流 / 汇合 A 专题](../features/factory-conveyor-routing-v1.md)。V4 勘探世界使用 `factory_3d / 4 / factory_discovery_routing_v1 / factory_discovery_yard_64_v1 / factory_discovery_routing_starter_v1`。schema 4 增加物流附件、普通构件预算及共同仲裁时序；自动电网、配方、发现、统计和活动时钟沿用现行合同，不将旧世界静默解释为新物流。

字段基础见 [V2](factory-discovery-save-v2.md)，自动图检查见 [V3](factory-discovery-save-v3.md)，锁、候选恢复、原子发布见[共用保存合同](factory-world-state-and-save-v1.md)。本篇只定义 V4 增量；当前新建已随准入口采用 [V5](factory-admission-save-v5.md)，4→5 为独立显式选择。A 原执行结果见 [W41](../devlogs/2026-W41.md)，最新回归见 [W42](../devlogs/2026-W42.md)。

## 权威状态

| 对象 | 保存与严格约束 |
| --- | --- |
| kits | 原六类预算不变，加 `splitter=8`、`merger=8`；剩余构件 + 在场同类实体严格等于总预算；总实体上限 318 |
| 分流器 | `id/type/x/z/dir/cargo/progress/entry/batch/output_cursor`；type=splitter，1×1；后入、前 / 左 / 右出 |
| 汇合器 | `id/type/x/z/dir/cargo/progress/entry/batch/input_cursor`；type=merger，1×1；后 / 左 / 右入、前出 |
| 方向 / 游标 | dir 为东 / 南 / 西 / 北的 0–3；output_cursor 为前 / 左 / 右的 0–2；input_cursor 为后 / 左 / 右的 0–2；均为整数，不取模修复非法输入 |
| cargo | 空或 crystal / rich_crystal / catalyst / crust_solvent；容量一件；样本不能上带或附件 |
| progress / entry | progress 为有限数 [0,1]；entry 编码为两个整数的世界方向基向量，必须对应附件有效输入方向；空附件为 progress=0、entry=后方 |
| batch | 空货 / 原矿为 0；加工产物须有合法 batch；与反应器在制 / 输出、普通带及其他附件共同检查批次唯一与件数上限 |

附件出清时保留公平游标；空载旋转成功时清零本机游标并规范入口。附件不是仓储，不提供手动塞货 / 取货；拆回完整返回内部物料和构件，背包不足则拒绝整个事务。所有附件库存计入在途和持有量，经过附件不记产消事件。

原普通带字段保持，cursor 仍为来源实体 ID 边界，来源已拆除不等于存档损坏。schema 4 按稳定 ID 次序生成生产批次及序列化实体；空间索引、端口图、电网组号、空位快照、仲裁请求与容量预约均不保存。

## 调度、时间与数值

- 20Hz：供电 / 生产 → 冻结物流占用 → 成熟货物提出请求 → 最多三轮冲突仲裁 → 统一提交。机器出料与运输槽使用同一仲裁阶段；本步开始占用的槽不能在同一步被重新填入。
- 每源最多送一件，每目标运输槽最多收一件，新货物 progress=0，后续满 20 步才可转交。局部堵塞跳过、游标更新和竞争重试见功能专题；提交失败不得出现半件转移或提前更新游标。
- 原带的端口与一秒行程保持；机器补入刚腾空的带可能比旧算法晚一步。升级瞬间守恒，升级前后不承诺运输轨迹相同；同版同起点同命令和固定步数的恢复轨迹一致。
- 计数、ID、批次、游标严格整数。进度 / 时间 / 能量沿既有浮点模型与校验容差；JSON 跨进程比较使用现有发现检查的浮点容差，不将容差用于物品数量或非法字段。设计中的“轨迹一致”不要求十进制 JSON 往返后浮点位模式相同。
- 失焦继续生产和自动保存；主动 / 失败暂停保持；独立进程恢复不补离线时间。

## 显式升级与回退保护

1. 世界菜单分别提供“继续选中世界”和版本适用的升级按钮。旧 schema 2 / 3 可以继续原规则；2→3 自动电网与 3→4 物流为两个独立选择，不把两次变更合并成一个确认。
2. schema 3 升级说明各加八件附件、共同公平仲裁、补带可能多等 50ms、保留原档及新客户端要求。取消时不持有写锁、不改主档。schema 4 不再提供升级领取入口。
3. 准备阶段持有既有锁，按原 schema 3 全量校验，再在内存转换身份 / kits；保留世界 ID、名字、设备、物料、在制、普通带进度 / 游标、发现、电网、统计与活动时钟。新模型再次严格校验，自动图只在验证后核对重算结果，不修复伪造的缓存。
4. 正式场景重建后，重新核对来源及主档哈希。保留来源原文到 `backups/pre-routing-v3-<sequence>-<hash>.json` 并读回核验；不覆盖不同内容，不进入三个普通备份槽轮换。
5. 沿临时写入、严格读回、哈希复核与原子发布提交 schema 4，sequence 增加一次。备份、重建、校验、临时写入、读回或发布失败均保留旧主档和有效来源，调用方关闭失败会话并释放自己的锁。
6. 发现已声明 schema 4 的主档后，不能自动使用 schema 3 / 2 副本回退并覆盖；未来版本或未知规则 / 供给继续阻断所有备份回退。schema 1 与旧二维 schema 10 不迁移。

实现由 `routing_model.gd` / `logistics.gd` 承担新规则，`codec_v4.gd` 使用共用严格联合状态校验及专门附件字段检查；原 V1–V3 入口保留。所有迁移测试使用仓库隔离根，不能批量升级用户正式世界。
