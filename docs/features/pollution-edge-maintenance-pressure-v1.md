# Pollution Edge Maintenance Pressure V1

更新时间：2026-06-15

## 用途

本文是 [Demo Combat Progression V1](demo-combat-progression-v1.md) 下的可执行细专题，专门定义“后勤维护 / 基础过滤模块如何在污染边界读出第二个承压差异”。

本文是下一次相关代码开发的直接范围来源；`demo-combat-progression-v1.md` 保留阶段方向和边界，不再承载每日开发包细节。

## 玩家价值

玩家完成核心站后勤维护后，回到污染边界应能清楚感到本趟污染战斗或污染采集压力下降，并从 HUD、对象反馈、战斗日志和出发口读懂：回基地加工、整备和确认维护不是文案奖励，而会改变下一趟外勤风险。

## 与整体规划的关系

- 服务长期核心：“基地服务冒险，冒险反哺基地”。
- 覆盖 `demo-definition-v1.md` 中的角色成长、装备 / 模块、战斗压力、UI / HUD、存档 / 状态和自动检查规格。
- 承接已落地的出发整备台、基础过滤模块、模块校准、核心归档维护、后勤维护和污染边界回访压力。
- 作为 `Demo Combat Progression V1` 的第二个可感知差异，避免继续加厚同一条核心站归档后回访链。

## 当前已有基础

- 后勤维护状态已由 `FieldOutfittingRuntime` 写入出发整备台对象，并能在核心站复测中降低污染采集和反击承压。
- 污染边界已有多段复测 / 回访压力对象、受扰掠行体守卫、药剂消耗、污染沉积物、过滤器处理和浆液回收读法。
- `EnemyCounterattackRuntime` 已统一处理污染反击、抗污染药剂、模块校准、核心归档维护和后勤维护倍率。
- `DepartureReadinessFormatter`、`CoreGuardAftermathFormatter` 和 HUD / 地图 presenter 已能聚合出发准备和下一趟外勤目标。

## 本轮范围

本轮只做一个可验证开发包：

- 让已确认的后勤维护状态在污染边界压力段中读出承压差异。
- 覆盖至少一个污染采集或污染敌人反击结果，能比较确认前后的生命 / 防护损耗。
- HUD、出发整备台、外勤出发口、污染边界对象提示和战斗日志都要说明该差异来自后勤维护或整备台状态。
- 自动检查必须覆盖状态准备、压力段开放、确认前后损耗差异、反馈文本和存档状态判断。

优先复用现有污染边界回访压力点；只有既有对象无法表达玩家路径时，才在 `region.pollution_edge` 内新增一个小压力口袋，不新增区域、敌人类型或资源类型。

## 当前不做

- 不新增第 13 区域。
- 不新增资源、敌人类型、任务链、随机成功率、新货币、队员、完整装备栏或完整 `loadout`。
- 不扩前线行动台、行动候选、窗口复盘、高压窗口或 `base_action_state`。
- 不把本包做成纯提示修补；必须有真实承压 / 防护差异和自动检查。
- 不继续给核心稳定站完成态追加同构回访内容，除非本专题检查证明污染边界路径断档。

## 玩家操作路径

1. 玩家已完成基础过滤模块装配、模块校准、核心归档维护和后勤维护确认。
2. 玩家在基地通过 HUD、出发整备台或外勤出发口看到“后勤维护已接入，污染边界复测承压会下降”。
3. 玩家从既有外勤出发口回到污染边界，进入污染压力段或回访压力口袋。
4. 玩家采集污染沉积物或击败受扰掠行体；生命 / 防护损耗读取后勤维护倍率。
5. 战斗或采集反馈明确说明本次承压下降来自出发整备台后勤维护。
6. 后续反馈回指污染过滤器、前哨核心补给或下一趟外勤准备，不开启新任务链。

## 运行时、存档与数据边界

- 成长状态继续使用出发整备台地图对象上的后勤维护标记，不新增角色成长字段。
- 承压计算继续走 `FieldOutfittingRuntime` 和 `EnemyCounterattackRuntime`，不把倍率判断散落到 HUD、地图对象或提示 formatter。
- 如果新增污染边界对象实例，应使用稳定 `map_object_instance` / `enemy_instance` ID，并加入存档来源允许表和自动检查。
- 若检查脚本需要扩展，优先新增专项 check 文件，再由现有入口轻量调用；不要继续向 1500 行的 `vertical_slice_flow_check.gd` 堆大段逻辑。

## HUD / 场景 / 对象反馈

至少覆盖：

- 出发整备台：显示后勤维护已确认，并指出下一趟污染边界承压差异。
- 外勤出发口：把污染边界复测列为当前可观察收益之一。
- 主 HUD / 地图目标：在基地和污染边界分别读出准备状态与压力段目标。
- 污染边界对象提示：说明该采集或战斗会读取后勤维护收益。
- 战斗日志：明确说明损耗降低来自出发整备台后勤维护。

## 验收条件

- 玩家能通过真实操作获得后勤维护状态，并在污染边界读出第二个承压差异。
- 差异同时影响至少一种生命 / 防护损耗计算和对应反馈文本。
- 离开区域、回基地、再出发后，状态判断仍稳定。
- 自动检查覆盖状态来源、压力目标、损耗差异、HUD / 对象 / 战斗反馈关键文本。
- 未引入本专题“当前不做”中的系统扩张。

## 验证计划

- 客户端静态检查：`sh ./scripts/check-client.sh`。
- 涉及文档：`./scripts/check-docs.sh`、`./scripts/check-text-files.sh`、`git diff --check`。
- 若新增或调整 Godot 运行时检查，在确认本机 Godot 可启动后执行 `sh ./scripts/check-client.sh --with-godot`。

## 风险与后续决策

- 如果污染边界已有回访压力点过密，本包应优先改读法和承压来源，不再横向堆更多同类口袋。
- 如果后勤维护收益在污染边界仍不够可感知，下一步再评估遗迹外圈压力差异或建立角色技能 / 装备模块子专题。
- 若实现需要明显扩展地图脚本、HUD 脚本或提示 formatter，应先拆分职责再落地功能。
