# Demo Action Feedback Readability V1

更新时间：2026-06-17

## 用途

本文定义首版 Demo 动作反馈可读性第一版的范围。它不是试玩准备、修 bug 阶段、终局菜单、结算页或发布准备；它用于检查玩家执行采集、清障、建造、加工、整备、战斗和核心写入后，能否立刻从结果文本、HUD、地图和对象状态读出发生了什么、消耗 / 获得了什么、下一步应去哪。

## 玩家价值

玩家不应只看到“成功”或“失败”。每次关键动作后，他需要理解：

1. 本次动作造成的真实结果，包括资源、生命 / 防护、敌人、任务和对象状态变化。
2. 结果是否已经被 HUD、地图目标或场景对象同步读取。
3. 下一步应该回基地、继续外勤、补材料、处理敌人还是整理 Demo 完成成果。

## 与整体规划的关系

本专题覆盖 [Demo Definition V1](demo-definition-v1.md) 的「UI / HUD」「自动检查」「资源 / 生产链」「工艺 / 科技解锁」「战斗压力」规格。

它承接已完成的 [Demo Interaction Affordance V1](demo-interaction-affordance-v1.md)：交互可辨识度解决“动作前能否判断对象状态”，本专题转向“动作后能否读懂结果和下一步”，避免继续加厚对象可交互 / 已处理同类读法。

## 当前已有基础

- `GatherSystem`、`BuildSystem`、`ProcessingSystem`、敌人反击和核心写入路径已有结果 message。
- HUD、地图、对象提示和专项检查已能读取主线、资源链、场景、交互可辨识度和完成成果。
- 多个开发基线和 Godot runtime 检查已覆盖从新档到 Demo 完成后回前哨整理的代表断点。

## 本轮范围

- 检查代表性动作结果是否同时说明结果、消耗 / 获得、状态写入和下一步。
- 覆盖采集、清障、建造、加工、整备台确认、敌人击败、核心守卫缓存、核心设备写入和前哨整理动作。
- 检查动作后 HUD / 地图 / 对象提示是否继续指向真实目标，不新增 UI 面板。
- 新增检查优先放在独立专项文件，不继续推高 `vertical_slice_flow_check.gd`、`vertical_slice_map.gd`、`prototype_hud.gd` 或 `interaction_prompt_formatter.gd`。

## 第一包实施范围

- 新增窄职责 `DemoActionFeedbackFormatter`，为代表性动作结果统一生成 `success_feedback`。
- 接入采集 / 采样、清障、核心设备写入、敌人击败和前哨核心整理结果；建造与加工沿用既有 `success_feedback` 并纳入专项检查。
- 专项检查覆盖结果文本、HUD 日志摘要、对象状态、库存 / 资源变化、敌人状态和地图 / HUD 目标读法。
- 不改 HUD 布局，不新增结果面板，不新增存档 schema。

## 当前不做

- 不继续加厚交互可辨识度、撤离恢复、场景构成、完成成果整理或整段断点检查同类内容。

## 玩家操作路径

1. 前哨：恢复核心、建造 / 整备、加工基础补给后，结果反馈应说明状态写入和下一步。
2. 外勤：采集、清障、战斗和回收缓存后，结果反馈应说明获得物、承压变化和回基地理由。
3. 核心站：守卫战、守卫缓存和核心写入后，结果反馈应说明消耗、保留成果和回前哨整理方向。

## 运行时、存档与数据边界

- 不新增存档 schema，不迁移稳定 ID。
- 只读取既有 `WorldState`、`CharacterState`、库存、任务、敌人、对象和基础设施状态。
- 若动作结果和状态写入不一致，优先修真实写入或结果来源，不用额外提示掩盖错误。

## HUD / 场景 / 对象反馈

- 结果文本：关键动作必须说明成功 / 失败原因、资源 / 状态变化和下一步。
- HUD / 地图：动作后目标应继续指向当前真实路线。
- 场景对象：已处理、已建成、已击败和已写入状态应继续被视觉刷新读出。

- 代表性动作结果能和 HUD / 地图、对象状态或场景视觉互相印证。
- 未引入当前不做事项，新增检查走独立专项文件。
